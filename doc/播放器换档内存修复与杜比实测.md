# 播放器换档内存修复与杜比实测

日期：2026-09-21。承接《内存优化审查与高画质内存分析》，用户用例为 **BV1omoHYzEST**。实现记录：`openspec/changes/reduce-player-memory-churn`，待用户手测，未归档。

## 本轮修复

- 同 cid、同账号上下文切换清晰度时，复用已加载或正在请求的弹幕，不重复下载 XML、解析、合并和提交弹幕列表。在线请求使用独立内容 epoch，视频换档 generation 变化不会丢弃仍然有用的结果。
- 换内容、移除当前条目、关窗使旧结果失效。成功空档案也去重；请求失败后，下次换档可重试。不建立跨视频弹幕缓存，也不额外保留一份解析列表。
- 弹幕任务使用单线程专用池，取消未开始的旧任务，析构等待已开始的任务，减少并行中间数据与悬空对象风险。
- 增加默认关闭的播放诊断：设置 `BBHOUSE_PLAYER_DIAGNOSTICS=1`，每 5 秒输出解码方式、视频尺寸/像素格式/色彩标识、缓存字节、掉帧、Windows 私有提交量和总工作集。固定字段白名单不导出 Cookie、请求头、媒体路径、标题、签名地址或原生全量日志。

**这些修复减少重复工作，但没有消除杜比解码/渲染的主要内存台阶。** 没有用软解、RGBA8、降低缩放滤镜或清空工作集伪装成优化。

补充纠正上轮审查：`loadOnlineSubtitles()` 已由 `subtitleCatalogRequested_` 去重，`subtitleEpoch_` 不因画质切换改变。虽然函数每次被调用，已有字幕目录实际不会重复请求；本次保留此机制，不声称新增了字幕复用。

补齐媒体直连回归：当前libmpv的curl后端会在空代理配置下读取环境代理，初始化时禁用该后端并沿用显式直连的libavformat；旧版不支持该选项时兼容跳过。未修改画质/硬解默认参数。

## 真实杜比用例

通过用户指定 BV、既有凭据和现有 GET 端点取得实际可用档位，只下载 qn80 与 qn126 视频流各前 **64 MiB** 到项目 build 下，签名地址只留在 Python 进程内存，未发播放心跳、未读写观看库、未导出凭据。媒体前缀不完整，但足以覆盖本次头 15–20 秒播放；不是整片或长期稳定性验收。

FFprobe 确认 qn126：3840×2160、29.970 fps、HEVC Main 10、`yuv420p10le`、BT.2020、基底 HLG；**Dolby Vision profile 8 / level 7，RPU 存在，EL 不存在，compatibility id=4**。libmpv 解码后报告 PQ，实际硬解为 `d3d11va-copy`，渲染输入 p010。

运行环境：Intel Arc 140T，OpenGL 驱动 32.0.101.8861，libmpv v0.41.0-1049-g0b7ed670f。Qt 原生离屏 OpenGL + libmpv render API，固定 1920×1080 输出 FBO，`cache=no`、无音轨、QML、弹幕。统计是 **PrivateUsage 私有提交量**，不同于任务管理器“进程”页的活动私有工作集，未单独采 GPU shared/dedicated usage。

| 同 handle/context 的 20 秒阶段 | 实际格式 | 阶段私有提交峰值 MiB | 阶段末 MiB |
|---|---|---:|---:|
| 1080P qn80 | d3d11va-copy / nv12 | 315.48 | 313.14 |
| 4K 杜比 qn126 | d3d11va-copy / p010 | 1733.50 | 1679.23 |
| 返回 1080P qn80 | d3d11va-copy / nv12 | 876.65（过渡期） | 313.41 |

这个结果在真实杜比片源上重现了“高画质明显抬高、返回回落”，主峰值可独立于弹幕和网络缓存产生。返回基线接近首次1080P，但只测一轮，不能据此宣称长期泄漏测试完成。

## 解码线程与呈现后端对照

发现当前 DLL 的 `hwdec-threads` 默认 **4**，与上轮测的 `vd-lavc-threads` 是不同选项。同一杜比前缀，独立进程各播放15秒：

| hwdec-threads | 实际解码 | 私有提交峰值 MiB | 阶段末 MiB | 总渲染掉帧 |
|---|---|---:|---:|---:|
| 4（默认） | d3d11va-copy | 1691.51 | 1680.75 | 43 |
| 2 | d3d11va-copy | 1591.73 | 1564.16 | 36 |
| 1 | d3d11va-copy | 1538.24 | 1510.78 | 28 |

减少硬解线程能节省约100–153 MiB，仍有1.5 GiB级占用。短时离屏掉帧包含起播/着色器/调度，不能推导所有4K60设备的性能，因此本轮未修改生产默认线程数。

另外增加隐藏原生窗口的 **mpv `vo=gpu/gpu-api=d3d11/gpu-context=d3d11`** 比较工具：它可以实际得到 `hwdec-current=d3d11va`、`pixelformat=d3d11` 和 PQ，而不是 OpenGL render API 中强制 d3d11va 后退为软件解码。独立进程播放20秒，私有提交峰值 **1209.83 MiB**，阶段末 **1183.35 MiB**，探针报告渲染/解码掉帧均为0。相对 OpenGL copy-back 有进一步节省空间，但仍有GiB级占用；独立进程/15与20秒采样窗口不同，不将所有差值归为某一个缓冲池。此原生窗口不包含 Qt Quick 图层/弹幕/字幕/截图/全屏合成，**不能把给现有 FBO 加一项 gpu-api=d3d11 当作等价修复**。必须另行设计纹理共享或原生呈现与 Qt 覆盖层的集成，并验证 HDR 输出、截图和跨窗口生命周期。

完整白名单证据：`doc/evidence/dolby-memory-fix-2026-09-21.json`。可复现工具和命令见 `tools/memory-review/README.md`。

## 验证

- `local-player-test`：真实 worker/队列/XML parser 覆盖请求未完成时重复换档、成功复用、不同内容晚到隔离、账号变化、失败后重试和空结果复用；既有本地播放/Cookie隔离测试通过。
- `player-runtime-test`：诊断中放入假的 Cookie 哨兵，确认输出不含请求头/路径/元数据和哨兵；当前定向回归通过。
- `local-player-windows`：真实原生 OpenGL 视频像素、进度、SMTC 和重开测试通过。
- `openspec validate reduce-player-memory-churn --strict` 通过。
- 总集成验证：完整工程和regression-tests构建通过；最终CTest **46/46通过，110.72秒**。偏好测试中途间歇失败的边界见[总交付记录](内存优化修复与杜比用例验证.md)。

## 用户手测

1. 用 BV1omoHYzEST 固定窗口大小，1080P→杜比→1080P各稳定播放30秒，重复5轮，记录相同任务管理器指标；必要时同时采白名单诊断。
2. 保持弹幕开启，换档前后检查弹幕位置、暂停/拖动、倍速；检查 CC 字幕选择保留。切另一视频与关窗重开不得出现旧弹幕或旧字幕。
3. 检查杜比/HDR颜色、音画同步、全屏和截图。当前产品依然使用原解码/渲染默认值，不应期待本补丁把杜比主峰值降至 PotPlayer 水平。

原生 D3D11 整合与同文件 PotPlayer、相同 HDR 输出/窗口大小/内存口径的对比，是后续解决主要峰值的独立工作，尚未完成。
