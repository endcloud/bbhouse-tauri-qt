## 内核选择

继续使用项目现有 **libmpv**。直播给出的是包含音视频的 HTTP-FLV 或 HLS 流，libmpv 经 FFmpeg 可以直接播放，无需像点播 DASH 一样外挂音轨，也无需为直播增加 Qt WebEngine、DPlayer 或浏览器代理服务。

依据：

- `/Users/ziyu/Documents/b3/DPlayer/src/js/player.js` 的 HLS/FLV 分支实际分别委派给 `hls.js` 与 `flv.js`，DPlayer 本身提供播放器界面、控制和生命周期管理。`live: true` 调整直播控制展示，并非专用 B 站 API 适配器。
- `/Users/ziyu/Documents/code_g/260914/bbhouse-tauri-private/src/hooks/useLiveData.ts` 已完成 B 站取流适配，当前选择 HLS / fMP4 / AVC，并由 `Video.vue` 内的 Hls 播放。这一选择服务于 WebView 解码与媒体扩展环境，不构成原生 Qt 必须使用浏览器的理由。
- `/Users/ziyu/Documents/b3/wiliwili/wiliwili/source/api/video_detail_api.cpp` 通过 `getRoomPlayInfo` 获取协议/格式/编码；`presenter/live_data.cpp` 选择流；`activity/live_player_activity.cpp` 将 `host + base_url + extra` 交给已有 mpv。该参考实现直接拒绝未开播和轮播，也印证原生 mpv 链路可复用。

参考项目当前实现也有不宜照搬之处：tauri 动态 portal 的直播入口不是明确分页的关注全集接口；wiliwili 取第一条协议/格式/编码，且当前房间播放循环只尝试首个 CDN。Qt 应保留明确偏好、清晰度一致的候选链和失败回退；不要照搬其打印直播 URL 的调试语句。

## 已关注且正在直播的列表

主要依据 `/Users/ziyu/Documents/b3/bilibili-API-collect/docs/live/follow_up_live.md`。

采用 `GET https://api.live.bilibili.com/xlive/web-ucenter/user/following`，Cookie 鉴权，参数 `page=1…N&page_size=10&ignoreRecord=1&hit_ab=true`。每页有效上限是 **10**，不能假定设置 30/50 后服务端会服从。

响应 `data.list` 包含已关注主播的直播情况：`roomid`、`uid`、`uname`、`title`、`face`、`live_status`、`room_cover`、`area_name_v2`、`text_small`；分页元数据为 `totalPage`、`pageSize`、`count`，另有 `live_count`。`text_small` 直接作为服务端人气展示文本，不将其标为精确实时在线人数。

客户端仅保留 `live_status == 1`；`0` 未开播、`2` 轮播都不进入正在直播列表。必须按原始分页元数据遍历，某页筛选后 0 个房间不等于后面没有开播主播。`LiveApi::parseFollowed` 返回筛选后的 `rooms` 和原始服务端页的 `hasMore`，控制器负责继续加载及跨页去重；roomId/mid 始终使用字符串跨 QML 边界。

另有 `GET /xlive/web-ucenter/v1/xfetter/GetWebList`：`hit_ab=true` 文档声称可取全部开播主播，但封面、关键帧、人数和计数等字段会缺省；`hit_ab=false` 又只取前 10 个。为避免漏页和补查链路，本期选上面的分页接口。

tauri 参考链路是 `api.bilibili.com/x/polymer/web-dynamic/v1/portal` 的 `live_users.items[].mid` → `api.live.bilibili.com/room/v1/Room/get_status_info_by_uids`。后者支持 GET `uids[]` 或 POST `uids` 数组，返回以 UID 为键的对象，包含 room_id/uid/uname/face/title/cover_from_user/keyframe/live_status 等；当前新实现不依赖此补查。

## 直播取流

主要依据 `/Users/ziyu/Documents/b3/bilibili-API-collect/docs/live/info.md` 的“获取直播间信息”与上述 tauri、wiliwili 代码。

`GET https://api.live.bilibili.com/xlive/web-room/v2/index/getRoomPlayInfo`

| 参数 | 本期值 | 说明 |
|---|---|---|
| room_id | 房间字符串 ID | 支持由响应规范化真实房间 ID |
| no_playurl / mask | 0 / 1 | 与两个参考客户端保持一致 |
| qn | 默认 10000 | 用户选清晰度时重新请求，不能自行改签名地址 |
| platform | web | 网页取流形态 |
| protocol | 0,1 | HTTP stream、HLS |
| format | 0,1,2 | FLV、TS、fMP4 |
| codec | 0,1 | AVC、HEVC；本期 AVC 优先 |

官方收集文档称无需 Cookie，但应用传入当前凭据快照，让可用清晰度由服务端权限决定。API 走现有直连共享管线，绝不使用港澳台 PGC 代理快照。

数据路径：`data.playurl_info.playurl.stream[].format[].codec[]`。各层分别提供 `protocol_name`、`format_name`、`codec_name`；编码项含 `current_qn`、`accept_qn`、`base_url` 与 `url_info[]`，地址由 **host + base_url + extra** 原样串接。`g_qn_desc[]` 提供清晰度名称表。

常见 qn：80 流畅、150 高清、250 超清、400 蓝光、10000 原画、20000 4K、30000 杜比。菜单以选中可用轨的 `accept_qn` 为准，名称来自 `g_qn_desc`，不能仅凭全局名称表宣称用户拥有全部档位。服务端降级时显示 `current_qn`，备用流也只取同一实际 qn。

选择规则：优先满足请求 qn；在同档位内依次为 AVC FLV、AVC HLS/fMP4、AVC HLS/TS，再尝试 HEVC 对应格式。2026-09-19 调整为合并同清晰度所有轨后统一优先云 CDN、其他普通节点，mcdn/PCDN 留作最后备选；同类保留格式偏好，见 [后续修复](Windows任务注册与CDN优先级修复.md)。不同协议但实际 qn 相同的流也保留为失败候选。只允许有效的 http/https 地址，拒绝文件协议、用户信息、控制字符和不完整路径；媒体地址仅在内存中使用，不日志输出、不持久化。

加载媒体前检查 `live_status`、`is_locked`、`is_hidden`、`encrypted` 与 `pwd_verified`。休眠、轮播、封禁/隐藏、未验证密码和空流响应给出具体错误。播放器重连应重新取流，以获取新时效地址，并重查房间是否已下播。

旧 `GET /room/v1/Room/playUrl` 支持 `cid`、`platform=web|h5`、`qn`，返回 `durl[]` 与清晰度表；tauri 用它读清晰度再多次请求现代接口。本期现代接口已具备完整清晰度信息，无需重复请求每一档。

## mpv 接入约束

- 媒体请求使用直播 Referer `https://live.bilibili.com/` 与项目现有浏览器 UA，显式直连；API 和媒体均不能继承 PGC 区域代理。
- 将直播当完整音视频流加载，不传 DASH 音轨；不继承点播 `start`、倍速、字幕、历史上报、播放列表自动下一集或时长恢复逻辑。
- 实时流不提供普通 VOD 时间轴和拖动；“回到直播”应重新取流并重新 loadfile。暂停后继续是否跳到最新由直播专用控制器定义，避免点播 seek 语义。
- 复用现有 mpv 缓冲和硬件解码配置作为初始值。直播可设置较短的正向缓存，并关闭缓存回看；不要盲目应用全局 `profile=low-latency` 或零缓冲，以免引入丢帧/音画问题。流时长不确定，不能用 duration==0 判定加载失败。
- 流失败应先同 qn 换 CDN/格式；所有候选失败后提供重新取流入口。快速切房间、换档、关闭均需要世代号过滤晚到的网络/内核响应。
- FLV/HLS 实际起播、HEVC 硬解、音画同步、延迟、断网恢复仍需用户真实房间手测；离线 fixture 验证不能替代。
