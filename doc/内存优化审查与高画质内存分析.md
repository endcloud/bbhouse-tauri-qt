# 内存优化审查与高画质内存分析

审查日期：2026-09-21。基线：`93a79e9`（BBHouse 2.0.3）。

后续：用户已授权修复，实施与验证见[修复交付](内存优化修复与杜比用例验证.md)及[真实杜比实测](播放器换档内存修复与杜比实测.md)。本文保留修复前审查证据，不作为修复后状态。

## 结论

**`optimize-memory-footprint` 的方向合理，但 apply 尚不可靠，不能验收或归档。** 三页 GridView 虚拟化和非活动 Loader 释放已实现；页面状态恢复存在遗漏，动态池裁剪方向错误，现有测试不足以验证销毁重建。OpenSpec 格式校验通过不等于运行行为符合提案。

**已在本机隔离复现媒体管线的 GiB 级占用，重点应转向 `d3d11va-copy` 与 OpenGL 渲染路径，而非先归咎弹幕。** 用户确认显卡为 Intel Arc 140T，观察的是任务管理器“进程”页内存，切回后会回落，重复切换不累加。本次合成4K HEVC Main10、无页面/弹幕/网络缓存探针中，`auto-safe` 实际选择 `d3d11va-copy`，私有内存峰值1610.64 MiB（约1.57 GiB）。这支持高画质资源增长的判断，但不是用户真实杜比片源的完整归因，驱动/解码/中间纹理的占比仍须分项测量。

本次交付为审查与探索，未修改播放参数或产品行为。以下分别标注静态确认、离线复现和待测假设，避免把推测写成修复结果。

### 3. [P2] 动态裁剪把新加载的旧动态立即删掉

- 修复标准：显式从控制器同步初始分页状态，区分恢复与用户提交搜索。需覆盖“缓存桶直接返回，无新 pageInfoChanged”的场景。

### 5. [P2] 新销毁策略覆盖了尚未迁移状态的下载/关于页

- `MainWindow.qml:348-355` 也销毁下载与关于。`DownloadsPage.qml` 的搜索、媒体库/下载视图选择、页码仍是页面本地状态；返回时重置。关于页滚动不记忆，违反主规格明确的“导航关于页”场景。

### 6. 海报优化收益被误报，高 DPI 下还可能增加内存

`SeasonCard.qml:91-92` 新增 `显示尺寸 × DPR`。但变更前的 `3rd/FluentUI/Qt6/imports/FluentUI/Controls/FluImage.qml:22-25` 已使用 `显示尺寸 × min(DPR,2)`，因此常见 DPR≤2 时没有声称的“从原图全尺寸解码下降”的收益；DPR=3 时解码像素量相对旧上限约为 2.25 倍。应明确是否需要此清晰度取舍，并修正 SUMMARY 的收益说明。

### 其他需补测/澄清的边界

- 在线/动态移除了原本基于 contentHeight 变化的补载评估，现主要依赖 contentY；少量匹配、未满一屏时是否继续补载，需要专门 fixture，当前不将其列为已复现缺陷。
- 在线/热门裁剪后，JS diff 从首个不同 key 删除后续模型并重建，没有落实 design 的裁剪时机/视口稳定策略；“无跳动”尚无证明。
- Popular 的 `finishFetch()` 对所有档位应用 2000 条裁剪，而提案仅要求综合热门；当前其余服务端列表是否能达到上限未验证，应收窄条件。
- 动态 `zoneCache_`、同 aid 的 occurrence 明细，以及热门按期数缓存的多个 State，不受单个 2000 行上限全面约束。池有上限不等于全部会话数据有总内存上限。

## 为什么高画质可能增加数百 MiB 至 GiB

### 本机原生离屏实测

运行独立 Qt `QOffscreenSurface` + OpenGL 3.2 + libmpv render API，固定1920×1080输出FBO；显卡报告 `Intel(R) Arc(TM) 140T GPU (16GB)`，OpenGL驱动 `32.0.101.8861`。使用FFmpeg生成4秒24fps HEVC Main10，分别1920×1080和3840×2160，BT.709/BT.1886，无音轨、HDR或杜比元数据。`cache=no`，没有网络、账号、用户配置、字幕、弹幕和页面；每段采样6秒（含末帧keep-open）。探针按约100ms记录 **PrivateUsage（私有提交量）** 和整个WorkingSet，后者不是任务管理器默认的私有工作集。

| 单进程单次4K实验 | 实际解码路径 | 私有内存峰值 MiB | 说明 |
|---|---|---:|---|
| auto-safe，其他相关项auto | d3d11va-copy / p010 | 1610.64 | 初始化84.51 MiB；整个工作集峰值1616.42 MiB |
| auto-safe，hwdec-extra-frames=0 | d3d11va-copy / p010 | 1610.86 | 没有可见节省，不能盲目归因额外帧参数 |
| auto-safe，hwdec-extra-frames=4 | d3d11va-copy / p010 | 1604.86 | 与auto相近 |
| auto-safe，vd-lavc-threads=4 | d3d11va-copy / p010 | 1589.80 | 限制软件线程未明显改善该硬解路径 |
| 强制hwdec=d3d11va | **no** / yuv420p10 | 1477.54 | 本离屏OpenGL环境回退软件解码，不能当零拷贝成功 |
| hwdec=dxva2-copy | dxva2-copy / p010 | 1663.15 | 未改善 |
| auto-safe，vd-lavc-dr=no | d3d11va-copy / p010 | 1603.79 | 未明显改善 |
| auto-safe，fbo-format=rgba8 | d3d11va-copy / p010 | 1479.86 | 约少131 MiB，但本片为SDR；不可直接作为HDR/杜比生产默认 |
| hwdec=no，threads=4，仍有OpenGL渲染 | no / yuv420p10 | 1064.94 | 降低内存但换成软件解码，CPU/4K60体验未验收 |

同一handle与render context的 **1080P Main10 → 4K Main10 → 1080P Main10** 单轮试验：各阶段末值 **536.63 → 1350.45 → 668.73 MiB**，4K阶段峰值1361.14 MiB；最后阶段起始仍有1322.47 MiB过渡峰值，随后回落。各实验独立进程/分配历史不同，因此不能把单独4K的1610.64与切换实验1350.45混成同一条基线。这个往返与用户描述方向一致；只测了一轮，不声称已完成长期泄漏测试。

另一个无渲染`vo=null/hwdec=no/cache=no`对照：相同4K片源自动软件线程峰值750.62 MiB，4线程332.47 MiB，说明软件线程预算在**软件解码场景**可产生很大影响，不能外推到当前copy-back硬解路径。

测量局限：不是完整应用，未包含Qt Quick合成与实际屏幕呈现、真实B站DASH/杜比RPU；未采GPU独立/共享用量，也未做驱动分配栈追踪。部分探针记录0–5个渲染丢帧、解码器丢帧为0，离屏非显示同步且样本短，不能以此评判真实流畅性或参数优劣。`after_destroy`只表示mpv已销毁，Qt GL context/FBO尚存；残留数百MiB不能直接认定泄漏。所有这些限制不影响“没有弹幕/网页/网络缓存也能产生GiB级媒体内存”的实验结论。

**优先路径：**先验证应用实际运行时同样为copy-back，再比较与Qt/驱动兼容的原生D3D11呈现或互操作方案；当前简单地修改extra-frames/threads没有解决该硬解路径的峰值。不能为了省内存直接强制软件解码或RGBA8而牺牲4K60/HDR效果。

### 已确认的代码与运行库事实

- 切清晰度走 `PlayerController::setQuality()` → `startPlayback(..., true)` → `handleDashResolved()` → `ensureKernel()`；已有有效 client 直接复用，MpvClient 的 loadfile 使用 replace。没有发现每次选画质都新增一个常驻播放器的路径。
- `MpvVideoItem` 使用 `QQuickFramebufferObject` + libmpv OpenGL render API。Qt 侧一个输出 FBO不代表 libmpv 解码表面、参考帧、上传暂存、色彩转换和中间纹理只有一份。FBO 大小来自窗口项的物理像素，不是码流分辨率；窗口不变时，4K源增加的主要资源应继续在内部链路找。
- Windows 设置 `hwdec=auto-safe`，不保证特定硬解方式。MpvClient 已观察 `hwdec-current`，但控制器未消费这个信号作诊断。本次隔离实验确认copy-back，用户实际杜比播放会话仍需读取该属性核验。
- 点播没有显式 demuxer 缓存/解码线程预算；直播有独立的 32 MiB 设置，不能拿直播预算解释点播。
- 本机 DLL 离线初始化读取：mpv `v0.41.0-1049-g0b7ed670f`，FFmpeg `N-126580-g1f9ba3fb6`；默认 `demuxer-max-bytes=157286400`（150 MiB）、`demuxer-max-back-bytes=52428800`（50 MiB）、`demuxer-donate-buffer=yes`、`cache-secs=3600000`、`vd-lavc-threads=0`（auto）、`hwdec-extra-frames=auto`、`fbo-format=auto`。这些是运行库预算/选项，不是已分配内存，前后缓存还受共享/借用策略影响，不能简单相加当实占。DASH 外挂音频有独立 demuxer，要分别计量。

### 数量级解释（不是根因测量）

| 图像/表面 | 未计对齐与驱动开销的大小 |
|---|---:|
| 1920×1080，8-bit 4:2:0（NV12） | 约 2.97 MiB/帧 |
| 3840×2160，10-bit 装在 16-bit 容器（P010/YUV420P10） | 约 23.73 MiB/帧 |
| 3840×2160，RGBA8 | 约 31.64 MiB/张 |
| 3840×2160，RGBA16F | 约 63.28 MiB/张 |

因此 1080P 8-bit → 4K 10-bit 的单个解码表面理论上约 8 倍。假设某路径同时驻留 20 个 P010 表面，仅这部分就是约 475 MiB，再叠加解码/渲染中间资源与压缩缓存，可以出现明显台阶；**20 不是本次实测帧池数量，RGBA16F 也不是已确认的实际格式**。杜比标签本身不能告诉我们具体像素格式、profile 或硬解兼容性。

Arc 140T 为共享系统内存架构，仍应分别观察 Private Bytes、Private Working Set、GPU Shared/Dedicated Usage；这些口径可能交叠，不能直接相加。用户观察的“进程”页内存不能直接等同于所有 GPU 资源，也不能等同于全量已提交私有内存。

PotPlayer 的对照有价值，但必须用同一片源、编码/profile、HDR输出模式、窗口物理尺寸、硬解模式、缓存时长和相同统计口径。其实际渲染器/缓冲数尚未检查，不能直接宣称一定走 D3D11 零拷贝或低内存即画质等价。

## 后续优化优先级与验证方法

1. **先把真实解码路径变成可观察数据。** 在播放已稳定、换档前后、停止后采样：`hwdec-current`、`video-dec-params`/`video-params` 中尺寸/像素格式/色彩参数、解码器、`demuxer-cache-state`/缓存字节、丢帧、实际帧率；配合 Windows 私有/工作集与 GPU 内存。只输出字段白名单，不导出原生全量日志、Cookie、请求头或带签名地址。
2. **对高画质默认路径做 A/B。** 若软件回退，先解决硬解兼容性；若 copy-back，比较驱动可支持的直接解码互操作路径。只有在确认实际模式可用且色彩正确后才改变默认项。`vo=libmpv` 已固定 OpenGL render API，不能靠添加 `gpu-api=d3d11` 就把 Qt FBO 变成 D3D11 零拷贝；更换原生渲染后端属于独立架构提案。
3. **收紧点播压缩缓存预算。** 可实验前向 64 MiB/后向 16 MiB，并对照现默认；记录主视频与外挂音频实际缓存、网络抖动、拖动体验。这只能削减压缩缓存，不能用来证明已解决解码表面占用，也不应预先承诺省 1 GB。
4. **若确认为软件解码路径，实验线程预算。** 比较 auto、4、8 线程的私有内存/CPU/掉帧；高分辨率帧线程可能增加并行帧驻留。对硬解帧池只调整有明确证据的额外帧数量，不能任意压低规范要求的参考帧。每次只改变一个变量。
5. **同 cid 换清晰度复用弹幕和字幕数据。** `handleDashResolved():1058-1059` 每次重发弹幕/字幕加载；`loadDanmaku()` 同时持有 XML、解析列表、QVariant 投影，并再次触发合并与缓存重建。可以去掉重复请求和瞬时峰值，但需保持 seek/时钟、字幕选择、账号/内容切换隔离。相同内容降升画质都可能触发，故不能据此单独解释只在4K明显的峰值。
6. **弹幕预算要覆盖完整链路。** 16 MiB 仅 CPU 精灵缓存，不含每个在屏节点的 GPU 纹理、原始/过滤后条目与异步结果。相同文字的 GPU 纹理共享、重复转换减量、worker 输入/输出峰值可进一步优化；保持128个在屏项/每帧上传节流与旧generation隔离。不要以移除缓存换取卡顿。
7. **页面与会话总预算。** 修复本报告的恢复缺陷；按期数/UP/分区缓存采用有界策略，减少大 QVariantList → JS → JSON.stringify 全量投影和深比较。虚拟化只限制活跃卡片，并不自动消除所有数据副本。Qt/驱动缓存释放也不保证进程工作集立即等量下降。

建议基准矩阵：同内容 1080P SDR → 4K SDR → HDR10/杜比视界 → 1080P，窗口尺寸固定；分别关闭/开启弹幕，空闲10秒与稳定播放30秒采样，再重复5轮并关闭播放窗口。比较峰值、稳定值、回落、是否逐轮增长及掉帧。若稳定且回落，应报告高画质资源成本；若基线逐轮抬升，再按句柄/渲染上下文/worker/驱动跟踪泄漏。不能通过强制清空工作集伪造优化结果。
